Care Indeed V2 · Drive-First Evidence Architecture

Google Drive Canonical Evidence, Firestore Metadata, Serverless Commands

The production-target architecture for the Care Indeed Home Health Compliance application: Firebase Auth for identity, Firestore for operational metadata and state, Cloud Functions v2 as the server-side command authority, Google Drive as the canonical repository for evidence artifacts, and Google Cloud Storage strictly as temporary processing infrastructure.

View Architecture Phase 2F Migration Acceptance Gates

North Star

“Google Drive stores canonical evidence artifacts. Firestore stores evidence metadata and all normal operational state. Non-evidence records remain metadata only. Google Cloud Storage, when used, is temporary processing infrastructure and not a second evidence system of record.”

Firebase Auth Firestore Cloud Functions v2 Google Drive Canonical GCS Temporary Only

1. Executive summary

This document is the corrected architecture baseline for the Care Indeed Home Health V2 application (policy library, forms library, workflow library, mandated events, CES, Evidence Center, eCign, Journey/onboarding, Nolan, Brad, and administrative surfaces). It replaces the earlier draft that proposed a permanent, retention-locked Google Cloud Storage evidence bucket. That storage decision is no longer approved. The approved decision is Drive-first: the actual evidence files and deliberately generated final artifacts live in Google Drive; everything else is metadata.

1

Identity

Firebase Auth owns login. Firestore owns the Care Indeed profile, role, learner, supervisor, and assignment context.

2

Commands

Cloud Functions v2 are the server-side chokepoint for provisioning, evidence finalization, signatures, clearances, exports, repair, and audit.

3

State

Firestore stores users, assignments, attempts, deadlines, workflow tasks, approvals, and evidence metadata. Never file bytes.

4

Artifacts

Google Drive stores canonical evidence files, signed eCign packages, certificates, and final survey/audit packets. GCS is a temporary workbench only.

What the code already proves: the repository already has a working, server-side Google Drive evidence integration (server/googleDrive.ts, server/googleEvidence.ts) with a locked service-account identity, Shared Drive support, non-PHI folder conventions, packet publishing, and a CSV manifest. The Drive-first decision hardens what exists — it does not introduce a new evidence system.
Production honesty rule: identity, Journey state, and several review flows remain demo/local today. Until Phase 2F is implemented and verified, the application must not be presented as production security or an ACHC system of record.
Retired decision: there is no permanent production evidence bucket (the previously drafted cihh-prod-evidence-{env} is removed), no GCS Bucket Lock evidence retention, and no permanent GCS copies of signed forms, certificates, or exports. Any GCS object that outlives its processing job is an architecture defect.

Never stored in Firestore: file binary contents, base64 evidence bodies, full signed PDFs, raw signature images, entire packet contents, unnecessary PHI, or secret values. A pointer plus a hash is the maximum. This preserves the existing locked pointer-only contract from src/policy/evidence/storageProviders/types.ts.

Non-evidence domains are metadata only

Ordinary application records never automatically create Drive files. A non-evidence record may reference an evidenceId; it must never duplicate the evidence file.

Metadata-only domains (no Drive files, ever)

  • user records, learner profiles, supervisor relationships
  • assignments, module attempts, SCORM progress, quiz scores, deadlines
  • credentials metadata, policy definitions, policy-body source content
  • form-template definitions, workflow definitions and versions
  • event records, task records, approval records, notification records
  • calendar records, ordinary audit events, export-job records
  • upload-session records, UI preferences, analytics counters, dashboards

Evidence artifacts (Drive canonical)

  • uploaded supporting documents; completed/finalized evidence files
  • accepted evidence; signed forms; executed eCign packages
  • final signature artifacts; completed certificates
  • finalized policy acknowledgments when rendered as an artifact
  • final survey packets; deliberately generated audit packets and compliance exports
  • final immutable-by-application document versions
Important distinction: a form definition/template is application content (metadata). A completed, signed, or certified form PDF may be evidence in Drive. An audit event is structured server metadata; a deliberately generated audit packet may be an evidence artifact in Drive. An export job is metadata; its successfully completed final packet may be evidence in Drive. The authored policy corpus, generated TypeScript datasets, and source workflow Markdown stay in the repository — they are not migrated to Drive merely because they are documents.

8. Evidence workflow — adapter, not rebuild

The existing V2 evidence workflow is preserved: Evidence Center, WorkflowDrawer evidence capture, event/workflow/policy/task/form-instance linkage, the staged → submitted → accepted/rejected → superseded lifecycle, review controls, the evidence-complete certification gate, accepted-evidence read-only behavior, audit mode, and survey packets. The Drive/Firestore architecture lands behind these interfaces through a thin adapter.

Do not replace

  • Evidence Center as the central user workspace
  • WorkflowDrawer evidence panel inside CES/event work
  • Evidence lifecycle: staged → submitted → accepted/rejected → superseded
  • Evidence-complete gate for event certification
  • Accepted-evidence read-only and no-silent-delete behavior
  • Existing user-visible labels and review controls

Move behind it

  • local/demo evidence metadata → Firestore evidence documents
  • direct base64 upload → upload session + temp staging + evidenceFinalize
  • client-only acceptance → evidenceReview Cloud Function
  • soft role checks → custom claims + server checks
  • demo audit → append-only server audit entries
  • Zustand stores remain caches/compatibility layers — authority moves server-side

Evidence finalization flow (successful path)

 1. Authenticate actor (Firebase Auth).
 2. Validate App Check where enabled.
 3. Validate role and record scope.
 4. Create an idempotent upload session (uploadSessionId + commandId).
 5. Upload to temporary storage (or an approved equivalent).
 6. Validate object existence, type, size, and state.
 7. Scan where configured.
 8. Calculate SHA-256.
 9. Create or update the canonical Drive file (idempotent by commandId).
10. Verify Drive metadata and expected access.
11. Write Firestore evidence metadata.
12. Append server-side audit.
13. Mark the upload session complete.
14. Delete the temporary object.
15. Return the evidence ID and canonical Drive link.
Honesty rule: evidence is never marked accepted or available merely because a temporary upload succeeded. If the Drive write succeeds but the Firestore write fails, the session records enough state to reconcile the existing Drive file — a retry with the same commandId locates it (e.g. via Drive appProperties) and must not create a second file. The partial failure is audited and the record enters repair_required until reconciled.

9. Google Drive — the canonical evidence repository

Google Drive (a Workspace Shared Drive) stores the actual evidence bytes. The Drive fileId is the stable canonical locator; a stored webViewLink is refreshable presentation metadata, never the identity. This section hardens the integration that already exists in server/googleDrive.ts.

Verified existing integration (preserve and harden)

Already implemented in code

  • Service-account auth (Google Auth key file), Shared-Drive-aware queries
  • Locked identity: DRIVE_EVIDENCE_LOCK pins service account, project, Shared Drive; boot fails closed on drift
  • findOrCreateFolder (idempotent, cached), ensureFolderPath
  • Upload, upload-or-replace, copy, download, folder tree/children listing
  • Non-PHI name sanitizer + PHI-name tripwire (looksLikePhiName)
  • 01_CES top-level write lock until a readiness date (HTTP 423)
  • CSV Drive manifest + local fallback (server/data/drive-manifest.csv) with manifest upsert on every packet save
  • Calendar attachment indexing of Drive evidence refs

Hardening required for Phase 2F

  • Upload sessions + commandId idempotency (no duplicate files on retry)
  • SHA-256 stored on every evidence record; revision ID + modified time captured
  • Existence / trashed / access / moved / revision verification (see §11)
  • Supersede-with-history for accepted finals (replace-in-place is only acceptable for pre-acceptance drafts and regenerated non-final packets)
  • Orphan detection both directions (Firestore record ↔ Drive file)
  • Metadata updates that never change the evidence ID

Authentication model

The verified existing model is a dedicated service account (careindeed-drive-evidence@…iam.gserviceaccount.com) granted Content manager access on the organization's Workspace Shared Drive. This matches the actual tenant: files are owned by the Shared Drive (not an individual's My Drive), the key is server-side only, and no domain-wide delegation is required for the evidence write path. Browser users open evidence via Workspace permissions on the Shared Drive. If application identity (Firebase Auth) and Drive identity (Workspace) diverge for a given user, that is a launch blocker to resolve — not something to paper over with public links.

Approved credential direction — keyless impersonation: the external JSON key file is the local-development fallback only. The production target is keyless: the Cloud Run runtime identity (app project data-hangout-500409-j4) impersonates only this Drive service account (integration project orbital-stage-443721-v1) via short-lived IAM Credentials tokens (GOOGLE_DRIVE_AUTH_MODE=impersonation, fail-closed validation in server/googleDriveAuth.ts). Status: code prepared and tested; the scoped IAM binding and Cloud Run configuration are proposed only — not applied, not deployed. No permanent JSON key is ever deployed. See docs/DRIVE_KEYLESS_IMPERSONATION.md.
Never: public or “anyone with the link” evidence sharing; Google credentials in the browser; privileged Drive operations from the client. All privileged Drive calls are server-side.

Google Drive is not automatically WORM

Warning: ordinary Google Drive storage is not inherently WORM, object-locked, legally immutable, tamper-proof, or retention-locked. A Drive admin or a compromised account with sufficient permission can move, trash, or edit files. The protections below are application-level controls, and they are why the integrity checker (§11) exists. If regulatory or legal requirements demand true WORM retention, that is a separate archival-control decision that remains unresolved — and it must not silently reintroduce permanent GCS duplication merely to make an immutability claim.

Application-level accepted-evidence controls

  • Accepted evidence cannot be edited in place through the application
  • Accepted evidence cannot be silently deleted through the application
  • Correction creates a new evidence version referencing supersedesEvidenceId
  • The old evidence record remains available according to policy
  • SHA-256, Drive file ID, and Drive revision ID (when available) are stored

Detection and accountability

  • Actor and timestamp audited on every change
  • Permission changes audited
  • Integrity failures are visible, never masked
  • Legal-hold state represented in metadata (legalHold)
  • Destructive administrative repair requires explicit authorization and reason

Evidence link behavior

  • Every evidence link uses the canonical Drive reference: driveFileId for identity, a current webViewLink for display.
  • Links open in a new browser tab with target="_blank" and rel="noopener noreferrer".
  • No fake locally constructed URLs; no fallback to any permanent GCS URL (none exists).
  • A trashed or access-denied file is never shown as valid evidence — the UI shows a visible integrity error instead.
  • An authorized repair/relink workflow exists; repair and relink operations are audited.
  • The intended browser user's actual Drive access is verified under the chosen Workspace identity model before the flow is called complete.

10. Cloud Storage — temporary processing only

Google Cloud Storage may be used only as short-lived technical processing infrastructure. There is no permanent production evidence bucket, and no GCS path is ever the system of record for an artifact.

Approved temporary uses

  • upload staging and quarantine
  • MIME inspection and size validation
  • malware/security scanning
  • SHA-256 calculation
  • PDF generation, document rendering, format conversion
  • ZIP assembly for packet builds
  • failed-transfer recovery and retryable processing

Prohibited

  • a permanent evidence bucket (the drafted cihh-prod-evidence-{env} is retired)
  • permanent signed forms, certificates, or exports in GCS
  • GCS bucket/object paths as canonical evidence locators
  • Bucket Lock / retention lock as the selected evidence architecture
  • PHI, patient names, employee legal names, or diagnoses in object paths or filenames

Checker capabilities

  • Check a single evidence record on demand (e.g. before rendering a link or building a packet).
  • Scheduled sweeps (Cloud Scheduler → driveIntegrityCheck) with DRIVE_INTEGRITY_CHECK_SCHEDULE.
  • Administrative repair with dry-run reporting before any mutation.
  • Safe metadata refresh (webViewLink, revision, modified time) that never changes the evidence ID.
  • Non-PHI logs; all repair operations audited with actor and reason.
  • File contents are downloaded only when an integrity calculation (hash recompute) requires it and authorization permits it — never merely to refresh a link.

13. Survey packet and export generation

Packet generation reads canonical Drive evidence — never a permanent GCS copy (none exists) and never stale cached URLs. The existing packet pipeline (savePacketToEvent, QAPI/Admission renderers, manifest upsert) already publishes finals to Drive; Phase 2F adds verification, hashing, and export-job metadata.

Packet flow

 1. Create export-job metadata (/exports/{exportId}) — metadata only.
 2. Resolve accepted evidence through Firestore (by eventId / workflowId / status).
 3. Verify EVERY required Drive file (existence, not trashed, access, hash where required).
 4. Fail closed — or clearly identify missing/inaccessible evidence. Never silently omit
    evidence and still label the packet complete.
 5. Retrieve authorized artifacts server-side from Drive.
 6. Assemble the packet in temporary processing storage (packet-build/{exportId}/…).
 7. Calculate the packet SHA-256.
 8. Upload the finalized packet to Google Drive (exports/packets folder).
 9. Save final packet evidence metadata in Firestore (evidenceType: "final_package").
10. Append audit.
11. Delete temporary packet-build objects.
12. Return the canonical Drive evidence link.
Freshness rule: every packet-generation run refreshes or verifies current Drive metadata rather than trusting stale URLs. The final packet is not persisted in GCS — its only durable home is Drive, indexed by Firestore, and (as today) upserted into the Drive manifest.

16. Security controls

Layered controls: Firebase Auth, custom claims, Security Rules, App Check, Cloud Functions validation, service-account IAM, Secret Manager, application-level evidence locks, and server-generated audit. Rules protect client access; Functions protect business-critical mutations.

Authentication

Firebase Auth UID is the runtime identity. Production removes the demo fallback and binds every action to the authenticated user.

Authorization

Custom claims for broad roles; Firestore profile/relationship documents for supervisor and learner-specific scope. Every server command re-checks both.

Command validation

Functions re-check authorization, resource ownership, status, prerequisites, and lock state before writes. Hidden UI buttons are not security.

App Check

Protects callable functions and Firebase resources from unauthorized clients (APP_CHECK_ENFORCEMENT).

Storage boundaries

Clients write only to their own temporary staging paths. Canonical Drive writes happen only through the trusted server identity. No Google credentials in the browser.

Secrets

Drive service credentials live in Secret Manager (GOOGLE_DRIVE_CREDENTIALS_SECRET); no key files in the repo, no secrets in client-side Vite variables.

Command authority — server-side only

User provisioning, role changes, assignment finalization, completion finalization, evidence submission, evidence acceptance/rejection, evidence superseding, eCign execution, supervisor clearance, certification, overrides, audit append, packet finalization, Drive repair/relink, and access-permission changes are all server commands. None are direct client writes. No learner self-approval, no self-clearance, no self-certification, no Nolan/Brad/AI approval authority, no AI mutation of compliance records, no client-created audit events.

PII/PHI production gate: do not store real employee PII, patient PHI, or signature artifacts until the organization verifies the approved Google Workspace/Drive environment, contractual and legal posture (including BAA), service eligibility, access-control model, auditability, retention requirements, minimum-necessary design, incident response, backup/recovery expectations, security review, and compliance approval. Development and testing use mock or de-identified data only. PHI never appears in filenames, folder names, GCS paths, logs, task names, exception messages, test fixtures, screenshots, or AI prompts — and PHI is never sent to Nolan, Brad, Claude, another LLM, embeddings, or external analytics without an explicitly approved PHI architecture.

17. Security Rules strategy

Rules default-deny writes. Direct client writes may be allowed only for low-risk learner preferences or draft-only states. Compliance-affecting writes go through Cloud Functions.

Firestore rules posture — conceptual

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function signedIn() {
      return request.auth != null;
    }

    function isSelf(uid) {
      return signedIn() && request.auth.uid == uid;
    }

    function hasRole(role) {
      return signedIn() && request.auth.token.roles.hasAny([role]);
    }

    match /users/{uid} {
      allow read: if isSelf(uid) || hasRole('admin') || hasRole('hr');
      allow write: if false; // server function only
    }

    match /learners/{learnerId} {
      allow read: if signedIn() && userCanReadLearner(learnerId);
      allow write: if false; // server function only
    }

    match /events/{eventId}/{doc=**} {
      allow read: if signedIn() && userCanReadEvent(eventId);
      allow write: if false; // server function only — includes evidence metadata
    }

    match /auditEvents/{partition}/entries/{auditId} {
      allow read: if hasRole('admin') || hasRole('compliance');
      allow write: if false; // never client
    }
  }
}

Storage rules posture — temporary paths only

service firebase.storage {
  match /b/{bucket}/o {
    // The ONLY client-writable surface: the user's own temporary staging path.
    match /temporary-uploads/{uid}/{uploadSessionId}/{fileName} {
      allow write: if request.auth != null && request.auth.uid == uid;
      allow read: if false;
    }

    // Quarantine and packet-build paths are server-only.
    match /{allPaths=**} {
      allow read, write, delete: if false; // trusted service identity only
    }
  }
}

There are no evidence/, signatures/, certificates/, or exports/ permanent GCS rules — those paths do not exist in this architecture. Canonical evidence access control is Workspace/Shared Drive permission management plus server-side verification.

23. Final architecture statement

Practical final architecture: Firebase Auth = identity; Firestore = operational metadata and state; Cloud Functions = command authority; Google Drive = canonical evidence artifacts; temporary Cloud Storage = processing/quarantine only; Scheduler/Tasks = automation; Rules/App Check = client guardrails; Logging/Monitoring = operations; server audit = compliance traceability.
North star: “Google Drive stores canonical evidence artifacts. Firestore stores evidence metadata and all normal operational state. Non-evidence records remain metadata only. Google Cloud Storage, when used, is temporary processing infrastructure and not a second evidence system of record.”
