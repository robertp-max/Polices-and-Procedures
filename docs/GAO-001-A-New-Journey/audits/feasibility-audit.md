## 4. REUSE CHECK

Places where scenes reinvent something the engine/design or an existing component already provides.

| # | Finding | Where |
|---|---|---|
| 4.1 | **Modal/reveal-shell reinvented per-scene despite the architecture's own `<SceneModal>` primitive recommendation.** Scenes 2, 3, 6, 7, 8 each independently describe their own "backdrop dims / centered card / X-close" or "inline drawer / bottom sheet" pattern with scene-specific transition timings (150ms, 200ms, 250ms, 300ms — all different) — this is exactly the fragmentation the Design's own Section 3 ("4 independently hand-rolled overlay instances... strong candidate for a single `<SceneModal>` component") and Section 6 handoff list (`<SceneModal>` as a shared architecture-level primitive) were meant to prevent, yet each storyboard specifies its own bespoke timing/easing rather than referencing the shared primitive's contract. This isn't wrong per se (storyboards are allowed to describe *what* opens, not *how* it's coded) but the inconsistent numeric specifics (4 different fade durations for what should be one shared component) suggest these were authored independently without checking against each other or against a shared primitive spec. |
| 4.2 | **Audio synth reinvented conceptually per-scene, again despite the architecture's own `useSceneAudio()` recommendation.** Every scene names its own tone frequencies/pitch character ("lower pitch, non-alarming," "quiet affirming chime, distinct from Scene 4/6/8's judgment-correct chime") as if hand-tuning a bespoke synth per scene — this directly reproduces the exact problem recon documented as the reason two incompatible audio classes (`InteractiveAudioSynth` vs `SoftAudio`) already exist in the codebase. The Design's Section 3 explicitly calls for one shared `useSceneAudio()` hook with a named sound-effect enum; the storyboards, in practice, are speccing per-scene sonic identity rather than calling that shared enum, which reintroduces the divergence risk the whole exercise was supposed to close. |
| 4.3 | **Hotspot-registry pattern is correctly reused conceptually** (every scene describes a data-driven node array with position/discovery-trigger/concept fields) — this is the one primitive that *is* being reused as designed, consistent with the architecture's identification of `SCENE_HOTSPOTS` as "the most reusable idea in the whole pair." No finding here beyond confirming correct reuse. |
| 4.4 | **Choice-button correct/incorrect styling logic is not explicitly referenced as reusing `<ChoiceButton>`** in any storyboard's Audio & Microinteractions or Accessibility sections, despite being named as a shared primitive in the architecture's handoff list. Every scene (2, 3, 4, 6, 7, 8) independently re-describes "icon + text label + border-style, never color alone" as its own accessibility requirement rather than pointing at one shared component's built-in behavior — low risk since the requirement is stated consistently and correctly each time, but it's the same content copy-pasted 6 times rather than "inherits from `<ChoiceButton>`," meaning a future a11y fix would need to touch 6 storyboards' worth of bespoke implementations if `<ChoiceButton>` isn't actually built and used. |
| 4.5 | **Reset/replay (`resetProgress` equivalent) is not mentioned in any of the 9 storyboards.** The existing `CoreValuesInteractiveViewer.resetProgress()` (recon Section 2 primitives table) is the only existing reset affordance in either prototype, and the architecture spec doesn't carry it into `SceneConfig`/`useSceneEngine` explicitly as a required capability. None of the 9 scenes mention whether a learner can replay a scene after first completion (vs. only reopening completed nodes in read-only "review mode," which several scenes do specify) — this is a silent capability regression from Scene 4's existing prototype if not deliberately decided either way. |
| 4.6 | **Progress chip (`<ProgressChip>`) is reused by name/shape in most scenes** (progress rails, pips, "N/4 Solved" counters) but every scene reinvents its own visual metaphor (dots, pills, pins, platform-steps) rather than one shared component with scene-specific icon/count props — this is more defensible than 4.1/4.2 since visual variety across templates (JourneyMap vs. PuzzleBoard vs. FlowSequence) is an explicit design goal per the architecture's per-template layout table, but it's worth flagging that "visible progress indicator" as a *requirement* is being satisfied 9 different bespoke ways rather than 9 configurations of 1 component. |

## 5. PRIORITIZED FIX LIST

Ordered by blocking-risk to the build, not by document order.

1. **Resolve card-id addressability before writing any `SceneRegistry` discriminator.** Check `contentV2Adapter.ts`/`ACHC_Annual_Assembled.ts`/`CareIndeedOnboardingLMS.tsx` for a stable per-card id field. If one exists, every storyboard's `SceneNode`/discriminator design should cite the field name explicitly instead of leaving it as an open question. If one doesn't exist, add it to the content schema *first* — this blocks all 9 scenes equally and is currently unresolved in the design doc.
2. **Build the shell-side `sceneProgress[moduleId::lessonId]` persistence hook and `SceneProps.initialState`/`onProgress` wiring in `ModulePlayerScreen.tsx` as its own tracked shell change, before or alongside Scene 1**, not as an implicit dependency buried in 9 separate storyboards' QA-risk sections. Write one shell-change ticket, not nine restatements of the same missing capability.
3. **Decide and document the narration-audio production path (or explicitly descope it) before finalizing any scene's Field Notes/narration redundancy-contract split.** If audio production isn't funded/scheduled, strike the audio-tier language from all 9 storyboards' contracts and keep only the transcript/text tier — don't ship ~9,000 words of narration script design work whose only playback path is `speechSynthesis` browser TTS fallback (recon confirms this is the only thing that actually exists today for GAO-001-class modules).
4. **Fix `CoreValuesInteractiveViewer.tsx:1029` ("POLICY CO-CP-001 ATTESTED") and the §484.50 mis-citation at line 144 as a standalone defect ticket, landed before Scene 4's refactor**, so Scene 4's "must verify non-reintroduction" QA risk has something concrete to diff against rather than fixing it inline as part of a larger refactor PR where the deletion could get missed in review noise.
5. **Consolidate the 4 different modal/drawer transition-timing specs (150/200/250/300ms) and the per-scene bespoke SFX pitch descriptions into one shared `<SceneModal>` contract and one `useSceneAudio()` sound-effect enum before scene-specific storyboards are treated as final** — right now finalizing Scenes 2/3/6/7/8 as-written would lock in 5 different modal behaviors and reproduce the exact two-incompatible-audio-engines problem the architecture doc used as its central justification for building an engine at all.
6. **Add an explicit vertical-space budget check for the workspace region at `<lg` viewport width for Scenes 6 and 8** (the two scenes with 3+ stacked internal regions) against the shell's own already-collapsing 420px-rail-above-workspace layout, before committing to those scenes' described mobile stacking behavior — this is the one responsive-layout risk not covered by any existing prototype (both existing prototypes are single-canvas, not multi-region).
7. **Decide explicitly whether `canContinue`/`handleNext` gating on scene completion is required for any of the 9 scenes** (recon Risk #3, never resolved by the design doc beyond "default to non-blocking"). If any scene needs hard gating, that's the one `ModulePlayerScreen.tsx:1001-1009` edit needed — make this decision once, in the architecture doc, rather than leaving each of 9 storyboards to independently default to non-blocking without a signed-off product decision.
8. **Verify the two-store completion-write sync (recon Risk #5, `withLessonCompleted` + `useJourneyStore.recordLearnerCompletion`) is unaffected by any of the above changes**, since none of the 9 storyboards or the architecture doc currently mention this second store at all — a silent miss here would only surface as an admin-dashboard/completion-reporting discrepancy, not a learner-facing bug, making it easy to ship undetected.
