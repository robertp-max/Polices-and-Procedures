## 1. CURRENT NARRATION PIPELINE

**Where narration text lives (source of truth)**

- Runtime/content-v2 cards carry the same idea under different field names: `currentCard.narration_script` / `currentCard.transcript_text` (`src/v6/screens/pageviews/ModulePlayerScreen.tsx:953`, `:1134`, `:1391`, `:1629`). ## 3. CONSTRAINTS & OPPORTUNITIES for a 4-tier narration model

**What the current infra already supports**
- The schema already has a narration string per unit of content at multiple granularities: splash (`SplashCard.narration`), navigation card (`NavigationCard.narration`), each lesson card (`BaseCard.narration`), each challenge (`ChallengeContent.narration`), and final-test instructions/questions (`FinalTest.instructionsNarration`, `FinalTestQuestion.narration`) — `trainingContent.types.ts`. This is naturally close to "scene-start" (splash/nav), "node-unlock" (content card), and "feedback" (challenge feedback fields `feedbackCorrect`/`feedbackIncorrect`/`realWorldConsequence`, `:44-47`) tiers already, just not labeled as such.
- `app.location`-keyed lookups (`narrationAssetPath`, `hasNarrationAudio`, `mediaAssetPath`, `hasMedia`) give a uniform addressing scheme: any new tier of narration event can be given its own synthetic `app.location` suffix (e.g. `...scene-04.node-unlock.integrity`, `...scene-04.feedback.correct`) and slot directly into the existing manifest pattern without new plumbing.
- Playback UI primitives exist and are reusable: a play/pause `<audio>` ref pattern, a `speechSynthesis` browser-TTS fallback, and a text-tab "Narration Script" transcript view — all in `ModulePlayerScreen.tsx`.
- The CMS-485 precedent (`cms485AudioLocations.ts`) proves the team already has a working "generate a Set of authorized location keys, drop matching audio files in `public/assets/narration/`, gate playback with `hasNarrationAudio`" workflow that scales to a per-segment/per-step granularity (their existing `.s1.overview` / `.s1.delivery` / `.s1.challenge` suffixes already resemble 3 of the 4 proposed tiers).

**What must be added**
1. **Interactive scenes have no narration hooks at all.** `CoreValuesInteractiveViewer` and `GAO001Scene01WelcomeDesk` need new props/state to carry narration text (scene-start on mount, node-unlock per hotspot click, feedback per correct/incorrect answer, scene-complete on `isFullyComplete`/`showComplete`) — currently their only "audio" is UI sound-effect synths with zero relation to spoken narration or the `narrationManifest`.
2. **No event-tier vocabulary exists in the data model.** `trainingContent.types.ts` and the ContentV2 card shape have "one narration per card," not "N narration variants keyed by trigger type." A `NarrationTier` type (`'scene_start' | 'node_unlock' | 'feedback' | 'scene_complete'`) and a `narrationByTier: Record<NarrationTier, string>` (or per-hotspot equivalent) would need to be added to whatever schema backs interactive scenes, plus corresponding `app.location` suffixes so `narrationAssetPath`/`hasNarrationAudio` can resolve each tier's own audio file independently.
3. **No synced captions/timed transcript.** Current "transcript" is just the full script dumped as static text in a side panel — there's no per-sentence timestamp alignment, so a real captions track (for accessibility/ADA and for QA of TTS timing) is not supported today and would need to be built (e.g. WebVTT cues keyed to tier/segment).
4. **No audio-authoring/versioning trail for compliance.** There's no field capturing voice-approval status, script version, or recording date per narration string — only the blanket `narrationProductionStatus` message. For training-record auditability, each tier's narration text should carry its own stable ID + version + approval metadata, not just inline strings, so QA/compliance can trace "what script was read at what time to which trainee."

**How narration text should be stored for auditability**
- Keep narration as **structured, versioned text fields co-located with the content item** (not just embedded strings) — e.g. `{ id, tier, text, version, approvedBy?, approvedAt?, audioLocation }" — mirroring the existing `app.location`-keyed pattern so it flows into "the master CSV" mentioned in `trainingContent.types.ts:5`. Each tier (scene-start/node-unlock/feedback/scene-complete) should get its own stable, sanitizable location key (extending `narrationAssetPath`'s sanitization regex `[^a-z0-9._-]`) so the same CSV/export and the same `hasNarrationAudio` gating mechanism used for CMS-485 can be reused without new infrastructure — only the schema (tiers) and the interactive-scene components (currently narration-blind) need extending.
