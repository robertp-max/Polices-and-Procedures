## Deep Findings: FormViewer + FormSigningWorkspace Accessibility

### Positive Elements
- `FormSigningWorkspace` itself uses `role="dialog"` + `aria-modal="true"` when the signing workspace is active (good for the modal container).
- `getPrintableFormHtml()` performs a reasonable DOM clone + value sync for checkbox/radio/textarea/select/input values. This helps ensure the static snapshot shown to subsequent signers (DON reviewing what DON Assistant filled) contains the actual data. The snapshot mechanism supports the "I reviewed exactly what the previous signer attested to" defensibility argument.
- Some focus styles and basic keyboard handling (Enter for notes in WorkflowExecutionPanel context).

### Critical Gaps (Line-Level Code Issues)

**1. Weak Form Field Labeling (FormViewer.tsx — The Field Component)**
- The dynamic `Field` component (lines ~499-626) renders most inputs with `data-field-id` but **very limited proper labeling**.
- Labels are present (`<label className={labelCls}> {f.label} </label>`), but association is inconsistent:
  - For many field types (text, textarea, select), there is no `htmlFor` on the label or matching `id` on the input.
  - Inputs often rely on `placeholder` for identification (e.g., lines 369, 379, 386, 399, 409, 613, 571, 579).
  - Radio groups use `name={f.label}` (line 599) but lack `aria-labelledby` or proper fieldset/legend structure in many cases.
  - Help text (`f.help`) is rendered as a sibling `<p>` (line 620-622) with no `aria-describedby` linking it to the input.
- Result: Screen reader users (especially in the first-signer completion flow inside the WorkflowExecutionPanel drawer) will struggle to understand what each field is, especially in dense multi-section forms.

**2. Uncontrolled Inputs + Dynamic/Conditional Sections**
- The form is largely uncontrolled (native inputs without React state binding in the Field renderer).
- Dynamic/conditional sections (common in compliance forms) have no ARIA live regions or `aria-expanded` / `aria-controls` to announce when sections appear/disappear.
- Keyboard navigation can become trapped or confusing when conditional logic changes the form structure mid-completion (DON Assistant filling) or mid-review (DON reviewing the snapshot).

**3. Signature Fields and Multi-Signer Flow**
- Signature fields have `aria-label="Sign with eCign"` on the button (line 545 in FormViewer context), which is positive.
- However, once a signature is applied, the visual replacement (image + timestamp) has limited semantic markup for screen readers.
- In the multi-signer flow (FormSigningWorkspace:1514+ `isSubsequentSigner`):
  - Subsequent signers (DON) review a **static HTML snapshot** generated by `getPrintableFormHtml()`.
  - While the snapshot captures values, the cloned DOM may lose or weaken any original ARIA that existed.
  - There is no dedicated live region or status announcement when the "review the previous signer's completed form" view loads inside the signing workspace.
- This weakens the legal defensibility argument for users with disabilities: a DON using a screen reader may not have an equivalent "review experience" to a sighted DON.

**4. Focus Management and Drawer Integration**
- When FormViewer is rendered inside the WorkflowExecutionPanel right-side drawer (line 1757+), focus management is not robust.
- Opening the "Complete Form" or signing action does not reliably move focus into the form or trap it within the drawer.
- Closing the drawer or completing a form often loses focus entirely (no explicit return-to-trigger logic documented in the requirement row or drawer close handlers).
- This is especially problematic in the already dense WorkflowExecutionPanel (requirement rows + evidence + signer tasks + "Related Tasks" tab — one of the verifyUnifiedTaskProjection fails).

**5. Live Regions and Status Announcements**
- Minimal use of `aria-live` for signing progress ("signature applied", "document locked", "form instance status changed").
- When a first signer (DON Assistant) completes the form and triggers the eCIgn flow, or when a subsequent signer (DON) finalizes, there are no polite or assertive announcements for status changes that would be visible to screen reader users.
- This compounds the P0-01 multi-signer artifact identity problem: not only is the artifact chain fragmented, but the user experience of "what just happened to this form instance" is inaccessible.

**6. Contrast and Visual Design in Signing UI**
- The signing workspace and certificate views use dense text, borders, and status indicators.
- Combined with the known PM-layer design token inconsistency (slate palette instead of `--ci-*` tokens), contrast in low-light or high-zoom scenarios is at risk.
- The "review the completed form" snapshot view inherits whatever contrast issues existed in the original FormViewer rendering.

## Impact on eCIgn Legal Defensibility (Tying Back to P0-01 and Earlier Gaps)

- **First signer (DON Assistant) completion flow**: Weak labeling and keyboard support in FormViewer inside the WorkflowExecutionPanel drawer means users with disabilities may not be able to reliably complete and attest to forms. This weakens the "intent + review + attestation" chain for that signer.
- **Subsequent signer (DON) review flow**: The static snapshot is a reasonable design for "I reviewed exactly what was presented," but if the snapshot itself has poor semantic structure (cloned from a form that lacked proper ARIA), screen reader users reviewing the "completed" form may not have an equivalent experience. This directly impacts the defensibility of the second signature.
- **Overall multi-signer evidence**: The P0-01 artifact identity problem (multiple signed_package EV- IDs for the same canonicalFormInstanceId) is made worse when the user experience of creating/reviewing those artifacts is not accessible. An auditor or lawyer can fairly ask: "Was every signer given an equivalent opportunity to review and attest?"

This is a material gap for legal defensibility in a system that handles clinical and compliance evidence.

## Link to Declutter / Task Bloat

- FormViewer is rendered inside the already-cluttered WorkflowExecutionPanel drawer (requirement rows + evidence hierarchy + signer tasks + "Related Tasks" tab).
- Adding a dense, poorly-labeled form into that environment increases the "too many objects" and "messy" perception.
- The declutter proposal (composite "Form + Signers" requirement grouping + removal of the Related Tasks tab) would directly improve the accessibility of the drawer by reducing the number of competing interactive objects a keyboard user must navigate.

## Updated Recommendations (Accessibility + eCIgn + Declutter Synergy)

**High Priority (eCIgn Legal Defensibility):**
- Add proper `htmlFor`/`id` associations, `aria-labelledby`, and `aria-describedby` to all dynamic fields in the FormViewer `Field` component.
- Add `aria-live` regions for signing status changes ("signature applied", "document locked", form instance status).
- Improve focus management when FormViewer opens inside the WorkflowExecutionPanel drawer (move focus into the form, trap if appropriate, return focus on close or completion).
- Ensure the `getPrintableFormHtml()` snapshot preserves or enhances semantic structure (headings, labels, ARIA) so that subsequent signers reviewing the static version have an equivalent accessible experience.
- Keyboard navigation testing and enhancements for conditional/dynamic sections in FormViewer.

**Medium Priority (Full App + Declutter Synergy):**
- Apply the same rigorous ARIA + focus + live region standards to iAdministrator, AuditModePage, MasterCalendar/Gantt, and dense PM views.
- Use the declutter proposal (composite requirements, removal of redundant "Related Tasks" tab) as a forcing function to simplify the surfaces that need accessibility hardening — fewer objects = easier to make accessible.
